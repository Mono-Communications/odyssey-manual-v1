## <mark style="color:blue;">1. 증상</mark>

* **발생 시각** — 언제부터 언제까지 발생했는지
* **건수** — 특정 시점에 몰렸는지, 전체 메시지인지 일부 메시지인지
* **메시지 타입** — SMS / LMS / MMS / RCS / 카카오 등
* **Odyssey 버전** — <mark style="color:red;">**`application.yml`**</mark> 의 `common.version` 또는 실행 JAR 파일 이름 (예: `odyssey-1.0.10.jar`)

## <mark style="color:blue;">2. 로그</mark>

* 문제가 찍힌 **로그 한 줄**을 그대로 복사해 전달합니다. (예: `ERROR` · `WARN` 줄, 실패한 **`MSG_ID`** 가 들어 있는 줄)
* 그 로그가 들어 있는 **로그 파일**을 함께 전달합니다.

<table><thead><tr><th width="330">파일</th><th>내용</th></tr></thead><tbody><tr><td><mark style="color:red;"><code>logs/live/system.log</code></mark></td><td>전체 로그 (기본으로 전달)</td></tr><tr><td><mark style="color:red;"><code>logs/live/error.log</code></mark></td><td>에러 로그</td></tr><tr><td><mark style="color:red;"><code>logs/backup/</code></mark></td><td>지난 날짜의 로그. 발생 시각이 오늘이 아니면 해당 날짜의 파일을 전달</td></tr></tbody></table>

로그 파일의 종류와 주요 로그 메시지는 [22. 로그 / 에러 분석](22..md) 을 참고하세요.

## <mark style="color:blue;">3. 설정 파일</mark>

* <mark style="color:red;">**`config/application.yml`**</mark>
* 이중화를 사용하면 <mark style="color:red;">**`config/ha.properties`**</mark>

{% hint style="danger" %}
설정 파일에는 DB 접속 비밀번호와 게이트웨이 계정 정보가 들어 있습니다. 전달하기 전에 **비밀번호, API 키 등 비밀 값은 지우거나 `****` 로 가려 주세요.** (예: `password`, `sp-pwd`, `api-pw`, `api-key`, `rcs-secret`, `rcs-stat-secret`, `DB_PASSWORD`)
{% endhint %}

## <mark style="color:blue;">4. DB 조회 결과</mark>

문제 메시지를 아래 SQL 로 조회한 결과를 전달합니다. MySQL · MariaDB · PostgreSQL · Oracle · SQL Server 에서 같은 문장으로 실행합니다. `ODYSSEY` 는 실제 발송 테이블 이름으로, `12345` 는 문제 메시지의 **`MSG_ID`** 로 바꿉니다.

```sql
SELECT MSG_ID, MSG_TYPE, STATUS, RESULT, KKO_RESULT, RCS_RESULT,
       RESULT_DESC, TRACKING_ID, SCHEDULE_TIME
FROM ODYSSEY
WHERE MSG_ID = 12345;
```

발송이 끝나 이관된 메시지는 발송 테이블에 없습니다. 조회 결과가 없으면 로그 테이블 `ODYSSEY_LOG`(또는 기간별 로그 테이블, 예: `ODYSSEY_LOG_202611`)에서 같은 SQL 로 조회하세요.

<table><thead><tr><th width="330">컬럼</th><th>설명</th></tr></thead><tbody><tr><td><strong><code>MSG_ID</code></strong></td><td>메시지 고유번호</td></tr><tr><td><strong><code>MSG_TYPE</code></strong></td><td>메시지 타입</td></tr><tr><td><strong><code>STATUS</code></strong></td><td>처리 상태</td></tr><tr><td><strong><code>RESULT</code></strong> / <strong><code>KKO_RESULT</code></strong> / <strong><code>RCS_RESULT</code></strong></td><td>결과코드 (<strong>숫자 그대로</strong>)</td></tr><tr><td><strong><code>RESULT_DESC</code></strong></td><td><strong>실패 사유 문구 전체</strong> — 가장 중요</td></tr><tr><td><strong><code>TRACKING_ID</code></strong></td><td>접수번호 (비어 있는지 여부)</td></tr><tr><td><strong><code>SCHEDULE_TIME</code></strong></td><td>발송 예정 시각</td></tr></tbody></table>

결과코드의 의미는 [26. 결과코드 매뉴얼](26.-result-codes.md) 을 참고하세요.

## <mark style="color:blue;">5. INSERT 문</mark>

발송을 위해 발송 테이블에 직접 INSERT 했다면, **실행한 INSERT 문을 그대로** 전달해 주세요. 입력한 컬럼과 값에 따라 발송 경로와 결과가 달라지므로 원인 확인에 필요합니다.

* 수신번호 등 개인정보는 가려서 전달해도 됩니다. 다만 **컬럼 목록과 값의 형식**(자릿수, 날짜 형식, JSON 구조)은 그대로 남겨 주세요.
* 발송 프로그램이 INSERT 하는 경우에는 프로그램이 실제로 실행한 SQL 을 전달합니다.
* INSERT 예시는 [17. 메시지 타입별 INSERT](../part-3./17.-insert/) 를 참고하세요.
