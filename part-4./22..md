# 22. 로그 / 에러 분석

### <mark style="color:blue;">Odyssey 로그 파일 구성</mark> <a href="#id-22-1-odyssey" id="id-22-1-odyssey"></a>

**Odyssey**의 로그는 **`logs/live/`** 폴더 혹은 **`logs/odyssey-pipeline.out`**&#xC5D0; 출력되며, 일별로 압축되어 **`logs/backup/`** 폴더에 보관됩니다.

주요 로그 파일은 다음과 같습니다.

| 로그 파일                      | 내용                                                        |
| -------------------------- | --------------------------------------------------------- |
| **`system.log`**           | **전체 로그(catch-all)** — 모든 서비스 모듈 + HA 모듈 + Spring/DB 등 전반 |
| **`error.log`**            | 에러 전용 로그 (장애 발생 시 우선 확인)                                  |
| **`collect.log`**          | Collector 모듈 — 발송 테이블 수집 결과                               |
| **`fetch.log`**            | 발송 완료 메시지의 로그 테이블 이관                                  |
| **`reporter.log`**         | 리포트 처리 (수신 결과 콜백)                                         |
| **`router.log`**           | Router 모듈 — 메시지 라우팅, 채널 분기                                |
| **`sender-kt-legacy.log`** | KT 크로샷 발송 (SMS/LMS/MMS, legacy socket)                    |
| **`sender-kt-rcs.log`**    | KT RCS Hermes 발송                                          |
| **`sender-mn-kko.log`**    | 카카오 알림톡/친구톡 발송                                            |
| **`sender-cpaas-*.log`**   | CPaaS API 발송/리포트 (legacy/kakao/rcs)                       |
| **`trace.log`**            | 개별 메시지의 발송\~결과 수신까지의 과정을 추적                               |
| **`odyssey-pipeline.out`** | JVM 콘솔 안전망 — Spring 부트 init, JVM 크래시 등 logback이 못 잡는 출력   |

{% hint style="info" %}
<mark style="color:red;">**`system.log`**</mark>는 모든 모듈 로그를 통합해서 받는 전체 로그입니다. 특정 채널/모듈만 추적하고 싶을 땐 위의 모듈 별 파일을 참고하세요.

로그 파일 명은 logback 설정에 따라 환경별로 다를 수 있습니다. 정확한 파일명은 운영 환경의 **`logs/live/`** 폴더를 확인하시기 바랍니다.
{% endhint %}

### <mark style="color:blue;">로그 파일 백업 · 삭제</mark> <a href="#id-22-2-odyssey" id="id-22-2-odyssey"></a>

* 백업 위치 · 이름 : **`logs/backup/yyyy-MM-dd/<이름>_<번호>.log`**
  * 환경변수나 시스템 프로퍼티 `LOG_ROOT` 로 변경 가능
* 백업 시점
  * 1일 : 자정 이후 첫 로그가 기록될 때 전날 로그 백업
  * 50MB 초과 : 로그 파일이 50MB 를 넘으면 그 시점에 백업
* 보관 기간 : 30일
  * `trace.log` 는 7일간 보관 후 삭제

### <mark style="color:blue;">주요 로그 메시지</mark> <a href="#log-messages" id="log-messages"></a>

| 레벨    | 로그 메시지                                                                 | 의미 · 조치                                                                                                                                              |
| ----- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| WARN  | `[Accounts] ... 실행이 켜져 있지만 등록된 계정이 0개`                                  | (기동 시) 사용 설정된 메시지 그룹에 발송 계정(세션)이 없습니다. 수집된 메시지는 발송되지 않고 실패 처리됩니다. **`sessions`** 설정을 확인하세요.                                                       |
| WARN  | `[Collect] common.execute.<타입> 가 켜져 있지만 common.tables.fetch-count.<타입> 가 0` | (기동 시) 해당 타입은 수집되지 않습니다. **`fetch-count`** 값을 설정하세요.                                                                                               |
| INFO  | `[KtSession-n] req_report 처리 customId=... result=0 duration=...`       | KT 크로샷 최종 발송 결과 수신 (성공). `duration` 은 VMS 통화 시간(초)이며 문자는 `null` 입니다.                                                                             |
| WARN  | `[KtSession-n] req_report 최종 발송 실패 customId=... msgId=... result=...`    | KT 크로샷 접수는 됐으나 최종 발송 결과가 실패입니다. `result` 값은 **`RESULT`** 컬럼에 저장됩니다. ([24. 전송 결과 및 참고자료](24..md) 참고)                                             |
| INFO  | `[FetchPoller] archive 완료 count=... time=...ms`                        | 발송 완료 메시지를 로그 테이블로 이관했습니다.                                                                                                                        |
| WARN  | `[FetchPoller] archive 실패 - 로그 테이블에 적재되지 않아 STATUS 9 로 바꿔 ... 에 남김`     | 해당 메시지를 로그 테이블에 넣지 못해 **`STATUS 9`** 로 발송 테이블에 남겼습니다. `cause=` 의 원인을 확인하세요. ([18. MSG\_TYPE / STATUS 코드](../part-3./18.-msg_type-status.md#status-9) 참고) |
| ERROR | `[FetchPoller] 로그 테이블 생성 실패 logTable=... count=...`                    | 로그 테이블을 만들지 못했습니다. 해당 메시지는 **`STATUS 9`** 로 남습니다. DB 계정의 테이블 생성 권한을 확인하세요.                                                                      |
| INFO  | `[PipelineHistory] 파이프라인 오류 없음 (통신사 최종 발송 결과와 무관) - 트래픽 적재 생략`          | 해당 발송 구간에 Odyssey 내부 처리 오류가 없었다는 뜻입니다. 통신사 최종 발송 결과의 성공 여부와는 관계없습니다.                                                                          |
| WARN  | `[Shutdown] 5초간 드레인 진전 없음 — 대기를 중단합니다. routePending=... sendPending=...` | (정지 시) 처리 중인 건수가 줄지 않아 종료 대기를 끝냈습니다. DB 등 외부 연동 상태를 확인하세요. |
| WARN  | `[Shutdown] 최대 대기시간 60초 초과. 큐에 남은 메시지는 수집 전 상태로 되돌린다.` | (정지 시) 60초 안에 처리가 끝나지 않았습니다. 큐에 남은 메시지는 수집 전 상태로 되돌립니다. |
| WARN  | `[Shutdown] 큐에 남은 미발송 메시지 ...건 중 ...건을 수집 전 상태로 되돌림` | (정지 시) 발송하지 못한 메시지를 되돌렸습니다. 다음 기동 때 다시 발송됩니다. 두 건수가 다르면 **`recovery/`** 폴더를 확인하세요. |
| ERROR | `[Shutdown] 미발송 메시지 되돌리기 실패 - recovery SQL 로 남김 count=...` | (정지 시) DB 로 되돌리지 못해 **`recovery/`** 에 SQL 파일을 남겼습니다. 다음 기동 때 자동으로 실행됩니다. |
| WARN  | `[KtSession-n] req_report 미매칭 — 재기동 전 발송 건으로 보고 결과 반영 customId=... msgId=... result=...` | 재기동 전에 KT 로 보낸 메시지의 결과가 재기동 뒤에 도착해 반영했습니다. |
| WARN  | `[KtSession-n] req_report 미매칭 — msgId 복원 실패로 결과 폐기 customId=... result=...` | 어느 메시지의 결과인지 알 수 없어 반영하지 못했습니다. |
| INFO  | `[ReportWorker] 복원 결과 반영 msgId=... result=...` | 재기동 뒤 도착한 KT 결과를 발송 테이블에 반영했습니다. |
| WARN  | `[ReportWorker] 복원 결과 미반영 — 이미 만료/2차 진행 msgId=... result=...` | 재기동 뒤 도착한 KT 결과를 반영하지 못했습니다. 해당 메시지가 이미 다른 상태로 바뀐 경우입니다. |
| INFO  | `[ExpireCheckScheduler] KT 밀린 결과 수신 대기 — 만료 처리 보류 (기동 후 ...초 / 유예 300초)` | KT 직접 연동 환경에서 기동 후 5분 동안 만료 처리를 미루고 있습니다. 정상입니다. |
| INFO  | `[LbRefresh] 담당 digit 변경: ... (run mode=...)` | (이중화) 이 노드가 맡는 수집 구간이 바뀌었습니다. 장애 전환이나 노드 복귀 때 기록됩니다. |

{% hint style="info" %}
통신사 최종 발송 실패(결번, 전원 꺼짐 등)는 Odyssey 처리 오류가 아니므로 모니터링 화면의 실패 지표에는 포함되지 않습니다. 발송 결과는 발송 테이블의 **`RESULT`** 컬럼에서 확인하세요.
{% endhint %}
